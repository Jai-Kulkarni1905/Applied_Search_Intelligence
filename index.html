Which pages should an SEO team review first?

Testing whether a Random Forest can improve a simple rule for prioritizing pages for human content review.

Author Jai KulkarniLane Refresh Opportunity ScoringDate 29 August 2026Unit page within client
What the analysis found

The simple baseline was better at ranking the review queue.

The Random Forest did learn useful information about later page movement, but it did not beat the baseline on the primary held out test set at any of the seven K values that were evaluated.

Abstract

A content team can have thousands of pages to look at, but only enough time to review a small number of them. That makes the first question fairly practical: which pages should go to the top of the review list? I built a transparent scoring rule from the first half of March 2026, then tested whether a Random Forest using the same information could rank the pages better when the second half of March was kept aside as the outcome period. The learned model picked up useful signal and performed better than simply selecting pages at random, but the simpler baseline produced the better ranking on the main client held out test. The result is therefore less about replacing the rule with a more complicated model and more about showing that, for this dataset and this decision, a clear and inspectable ranking was already the stronger choice.

1. The problem

Which pages should be reviewed first?

This is the decision behind the project. A content or SEO practitioner cannot realistically inspect every page with the same level of attention. The useful output is therefore a ranked queue that puts the pages worth investigating near the top.

A wrong ranking has a simple cost. Time can be spent investigating a page that does not need attention, while a page with a meaningful problem can sit lower in the queue. The system is not intended to tell an editor to rewrite a page. It is intended to help decide where the editor should look first.

Research questionCan a learned model use the available search and traffic signals to produce a better review order than a transparent rule based score?

What was kept out

  • Future outcome fields were used only after ranking to construct and evaluate the label.
  • Trend fields such as trend_direction and trend_pct were not used as model inputs because they describe the movement being measured.
  • Pseudonymous IDs were used for joins, grouping and client based validation, not as predictive features.
  • Existing product decision fields were excluded so the model could not simply reproduce an existing FlyRank decision.

3. Methodology

The baseline

The baseline is deliberately simple. It estimates expected CTR within average position buckets and combines four signals: CTR need, visibility strength, position need and zero visibility need. Pages are then ordered by the resulting action score. The reason codes attached to the queue explain why a page was surfaced, including low CTR with meaningful visibility, insufficient visibility, unavailable position and pages that were not prioritized.

The Random Forest

The model uses nine features from the same 1–15 March information window: impressions, clicks, average position, organic sessions, AI sessions, CTR, encoded position bucket, expected CTR for the position bucket and average daily impressions. The client and content identifiers stay in the table for context but are not features.

What counts as a decline

A page receives is_declining = 1 when its average daily impressions from 16–31 March are lower than its average daily impressions from 1–15 March. This is an observed future outcome, not a label copied from a current product decision.

How the comparison was made

The main evaluation uses GroupShuffleSplit with the client as the group. Thirty clients are used for training and thirteen unseen clients are held out for testing. Both methods are evaluated on exactly the same test pages. Because the real output is a ranked list, the main metric is Precision@K rather than a fixed classification threshold.

Leakage check

The leakage audit was completed before interpreting model results. It checked that features came from the information window, that the target window did not overlap the feature window, that future outcome fields were not model inputs, and that product decision fields were not included. The modeling notebook also checks that the future period is absent from the feature dataframe.

What the model learned

The permutation importance results point mainly to visibility. Average daily impressions was the strongest contributor at 0.0844, followed by impressions at 0.0294 and CTR at 0.0139. Clicks contributed only 0.0017, while average position and the session based features added very little. Position bucket and expected CTR had negative importance under the held out evaluation.

5. Limitations and honest framing

  • This is a review ranking, not a refresh guarantee. A page being ranked highly means it deserves earlier investigation. It does not mean that changing the page will restore its traffic.
  • The decline label is narrow. It captures lower average daily impressions in the second half of March compared with the first half. It does not explain why the change happened.
  • Client generalization was tested, not universal generalization. The primary split holds out entire clients, and the five fold GroupKFold check also evaluates unseen clients. Results should still be understood as evidence from this warehouse snapshot.
  • A drop can have several explanations. Consolidation, seasonality, changes in the search results and ordinary noise can all look like a page decline. The queue should therefore be followed by diagnosis.
  • The model contains signal but did not earn its extra complexity. The Random Forest stayed above the held out base rate, yet the baseline won the operational comparison. There is no reason to replace a simpler method merely because a model is available.
  • The analysis is observational. It shows associations and ranking performance in the available data. It does not establish a causal effect of a content refresh and it does not describe Google's ranking algorithm.

6. Ranked recommendations

The result should be used as a triage system. A practitioner starts near the top, reads the reason attached to the page, checks the surrounding search context and then decides what to do.

01

Review the highest ranked pages first

Use the baseline queue to spend the first available review capacity on the pages it ranks highest.

02

Use the reason code to decide what to inspect

A low CTR reason points toward a snippet or intent review. Insufficient visibility means there may not be enough evidence for a CTR decision. Unavailable position means the position comparison cannot be relied on.

03

Diagnose before making a content change

Check whether the movement could be explained by consolidation, seasonality, search result changes, a recent update or low volume. A high queue position is a reason to investigate, not an instruction to rewrite.

04

Keep the learned model as evidence, not as the production queue

The Random Forest is useful for showing that the available signals contain predictive information. The evaluation does not support replacing the baseline with it.
